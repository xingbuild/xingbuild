# v0.26.19 发布证据契约与验证闭环方案

## 1. 目的

修复 v0.26.18 受控恢复暴露的发布控制面结构缺陷：资产、应用和媒体阶段虽然分别验证成功，但生产者返回的 phase 对象没有统一的 `result` envelope，`finalize` 读取另一种契约，导致完整公网证据被错误拒绝。

本版本不是给 `finalize` 增加特例，也不是手工补写 `result`。目标是让“阶段验证 → 证据聚合 → finalize”使用同一个不可变、可校验的证据对象模型，并用端到端测试证明成功和失败路径闭环。

## 2. 已核验事实与根因

- v0.26.18 的既有 `dp3ft6f6df8i` 未创建第二个 deployment，资产、应用、媒体验证均已返回成功事实。
- `verifyPublicPublicationAssets()` 返回 `verified: true`，但没有返回 `result: "verified"`。
- `verifyPublicSitePublication()` 将该原始返回值直接放入 `verificationEvidence.phases.assets`。
- `finalizeSitePublication()` 要求 `phases.assets.result === "verified"`，因此拒绝了本应完整的证据。
- 现有专项测试验证了整体结果、应用和媒体，但没有覆盖 `assets.result`，也没有覆盖“真实 phase 聚合 → finalize”正向闭环。

这说明问题在共享证据模型和边界验证，而不是 EdgeOne、网络、媒体文件、ContentSet 或页面 UI。

## 3. 目标对象模型

所有发布阶段只能产出统一的 `PublicationPhaseEvidence`：

```yaml
schemaVersion: publication-runtime-evidence-v4
publicationIdentity: <exact SitePublication identity>
attemptId: <stable attempt id>
phase: verifying-assets|verifying-app|verifying-media|verified|recoverable|failed
startedAt: <iso>
finishedAt: <iso|null>
result: running|verified|recoverable|failed
verified: true|false
lastEvidence: <phase-specific summary or null>
assets: <asset records, only for verifying-assets>
routes: <route records, only for verifying-app>
media: <media records, only for verifying-media>
failure: <failure envelope or null>
```

阶段生产者必须通过唯一 `createPublicationPhaseEvidence()` / validator（或等价单一模块）构造 envelope；调用方不得拼接裸 payload。聚合器只接受通过 validator 的三个 phase，并按固定顺序生成：

```text
assets verified → app verified → media verified → aggregate verified → finalize
```

v3 仅作只读兼容输入；任何进入 finalize 的新验证必须规范化为 v4，禁止 v3/raw 混合聚合。

## 4. 状态与证据不变量

1. `assets`、`app`、`media` 三个 phase 必须都存在、identity 相同、`result=verified`、`verified=true`。
2. 顶层 aggregate 只能由统一 reducer 生成，不能由调用者复制 phase 字段。
3. 任一 phase 失败，aggregate 必须是 `recoverable` 或 `failed`，不得是 `verified`，也不得进入 finalize。
4. `finalize` 只消费经过同一 validator 生成的 aggregate；不能仅凭 `lastEvidence` 或单 phase 通过。
5. phase 缺失、重复、顺序错误、schema 混用、identity drift、旧 raw asset payload、CAS revision drift 均在 finalize 前硬失败并保留 recovery evidence。
6. 失败状态必须原子写入 `state=recoverable|failed`，不得出现 `propagating + failure`。

## 5. 工程范围

允许修改：

- `scripts/lib/publication-assets.mjs`、`scripts/lib/publication-runtime.mjs`；
- `scripts/lib/site-publication-coordinator.mjs` 与唯一 publication evidence persistence；
- `tests/v02619-*` 及既有 runtime/coordinator/assets 测试；
- `VERSION.md`、package、current、design、history（由 Engineering 收口）。

明确不做：

- 不修改、回写、重试或删除 v0.26.18、v0.26.17、v0.26.16、`dp3ft6f6df8i`、`dp9g7iu2xbai`、旧 SitePublication、ContentSet 或内容事实；
- 不改 UI、IA、ResponsiveTextSlot、Why、正文、审核、来源、媒体或内容发布工具语义；
- 不新建第二套 resolver、publisher、evidence source；
- 不运行 content publish/ops-content，不直接调用 EdgeOne；
- 不以 sleep、盲目 retry、手工改 JSON 或 finalize 特判代替契约修复。

## 6. 验收合同

### 6.1 正向闭环

- assets/app/media 三个生产者均输出统一 v4 envelope；
- 统一聚合器生成完整 aggregate；
- `finalizeSitePublication()` 接受同一 aggregate；
- 同一 `sitePublicationId + snapshotHash + deploymentId` resume 仍幂等且不新建 deployment。

### 6.2 负向闭环

- assets 缺 `result`、app 缺失、media 缺失、raw payload、v3/v4 混用、phase identity drift、phase result 不一致、重复 phase、CAS 竞争均硬失败；
- failure、timeout、SIGINT/SIGTERM 后顶层为 recoverable/failed，保留 code/phase/lastEvidence；
- 资产 MIME/bytes/hash、HTML fallback、应用 root/main/h1/console/pageerror、媒体 status/MIME/non-HTML/bytes/hash 的原有分类继续有效。

### 6.3 门禁

Engineering 必须完成：

- `npm run check`、`release:prepare`、targeted v0.26.19 tests、分层 `release:qa`；
- `release:closeout-check`、exact `release:build`、`release:preflight`、`git diff --check`；
- 使用现有 v0.26.16 assembled client 做 content-enabled staging，覆盖五路由与 Robotaxi media；
- local commit/tag/clean + ProductArtifact 后停在产品/视觉独立验收。

产品/视觉批准后，才允许在既有 `dp3ft6f6df8i` 上再次一次性 resume；只在完整 v4 公网资产/app/media evidence 通过并 finalize 后通知 design-ui。内容 task/ops-content 在此之前继续冻结。
