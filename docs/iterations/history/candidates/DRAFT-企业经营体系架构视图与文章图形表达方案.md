## 1. 先回答根因：不是用户要求导致视觉失败

当前文章内图形的问题不是“文章形式”本身，也不是用户要求降低工程重复造成的必然结果。根因是我们错误地把三个不同问题压成了一个静态 SVG：

1. 架构视图：读者要理解系统层级、边界、类型、关系和下钻路径；
2. 文章插图：读者要理解本段文字回答的一个局部问题；
3. 内容发布能力：内容 task 要能更新文章和图源，而不改页面代码。

v0.19.0 解决了第3项，却把第1项降级成第2项的静态产物，结果是：

- 图形只有通用节点和线，没有 LikeC4 的分层边界、视图导航和对象语义；
- 大量空白卡片与自动布局空间消耗阅读面积；
- 内部 id（例如 `b2b-product-architecture`）泄漏到读者界面；
- 企业业务、产品、数据、技术、工程、运营和反馈被压在一张图中，粒度与关系类型混杂；
- 图形虽可由源文件重建，但“可重建”不等于“可阅读、可探索、可表达层级”。

因此这次纠偏属于产品与视觉建模责任，不应归因于用户的指令。

## 2. 目标读者与核心问题

### 2.1 企业经营体系读者

读者需要回答：

- 企业经营体系有哪些层级和边界？
- 当前看到的是总览、业务层、数字化实现层，还是某个系统内部？
- 一个对象为什么与另一个对象发生关系？
- 如何从总览进入下一层，再回到总览？

### 2.2 Robotaxi 产品与工程协作者

协作者需要回答：

- 哪些是业务对象、系统、组件、参与者或外部系统？
- 哪些关系是结构依赖，哪些关系是动作、事件、反馈或结果？
- 哪个视图来自 Robotaxi 权威模型，哪个只是 xingbuild 的网站展示快照？

## 3. 权威事实与边界

- 企业经营体系的概念、定义和关系：以 career 已确认框架和 xingbuild 批准同步快照为准。
- Robotaxi 的系统、业务对象、页面状态和运行事实：以 Robotaxi 仓库及其正式版本为准；xingbuild 不复制或编造 Robotaxi 业务模型。
- LikeC4 `.c4` 源是架构视图的可编辑语义源，不是事实来源本身；事实仍必须来自上游权威对象。
- Mermaid 继续用于流程、状态、生命周期和时序；不承担多层系统架构的主表达责任。
- D2 暂不进入本草案的当前实现承诺。

## 4. 单一推荐：LikeC4 多视图架构 + 文章局部解释

LikeC4 不再只是生成一张 SVG，而是作为架构视图的语义模型、视图集合和导航合同。官方 React 能力支持 `LikeC4View`、`ReactLikeC4`、多视图、节点点击导航、关系/元素详情和可控的平移缩放；BigBank 示例也证明了分组边界、类型化节点、关系标签和从元素进入下一视图的阅读方式。

推荐形成两层表达：

```text
企业经营体系文章
├─ 文章正文：解释概念、业务含义和经营闭环
├─ 文章内局部图：回答当前章节的一个问题，静态、响应式、可发布
└─ “打开架构视图”：进入 LikeC4 多视图架构浏览器
   ├─ Landscape / 总览
   ├─ Business / 企业业务架构
   ├─ Digital / 数字化实现
   ├─ Product / B端产品架构
   └─ 更深层的系统、组件或运营视图
```

文章图和架构浏览器是同一模型的不同投影，不是两份独立模型，也不互相替代。

## 5. LikeC4 架构浏览器的视觉合同

### 5.1 视图层级

- 总览只显示同一抽象层级的主体、边界和主要关系；不把所有下层节点塞入总览。
- 每个可下钻对象显式声明目标 view；点击节点进入下一层，返回恢复原视图与焦点。
- 每张视图只回答一个问题，节点粒度一致；不能同时把企业、系统、组件、操作和结果当成同类卡片。
- 反馈、结果和经营观察使用明确的关系/过程表达，不伪装成架构依赖。

### 5.2 视觉语言

- 使用 LikeC4 的 bounded context / system boundary 表达包含关系；边界不是装饰卡片。
- 使用节点类型、颜色、形状和标签表达 actor、system、component、external system 等语义；不要显示内部 id。
- 关系线必须具有稳定方向、可读标签和清晰端点；不同关系类型不能只靠线粗细猜测。
- 不使用大面积空白卡片、自动生成的内部 slug、无语义的统一浅色块或文章段落式图形。
- 鼠标移动、焦点和选中只改变克制的强调状态，不改变节点位置、连线路径或整体布局。

### 5.3 交互与可访问性

- 只读浏览；不允许读者编辑模型或保存布局。
- 桌面允许受控平移、缩放、复位和视图导航；这些是架构浏览能力，不是页面私有工具栏。
- 节点点击必须有键盘等价操作、明确焦点、返回路径和静态文本降级。
- 手机不把完整总览强行缩小；优先分层阅读或进入当前视图的全屏阅读层。
- 任何图形运行时失败都显示同源的视图标题、节点/关系清单和文章链接，不显示空白画布。

## 6. 文章内图形的责任

文章内图形继续使用 v0.19.0 的 source-driven figure 能力，但重新定义其视觉责任：

- 一张图只回答当前段落的一个问题；不承担完整架构浏览器的职责。
- 优先使用清晰的局部 LikeC4 view 或 Mermaid 流程图，不把完整九节点/十三关系图压进文章正文。
- 图形必须保留中文读者标签、层级标题、关系方向和 caption；禁止内部 id 泄漏。
- 图下提供“打开架构视图”的单一入口，进入同源架构浏览器；不在文章内重复实现节点点击和下钻。
- 内容 task 可以新增章节、局部图源和 caption；只有新增视图语法、运行时能力或安全边界时才进入 Engineering。

## 7. 与 B 端产品主页的关系

B端产品主页的 Robotaxi 互动展示是第三种表达模式，不应被误认为企业经营体系架构图：

```text
media-collection    → 原有多图/多模块展示能力，保留
interactive-stage  → 单行 Robotaxi 互动空间，新增
architecture-view  → LikeC4 多视图架构浏览器
article-figure      → 文章内局部解释图
```

本草案不删除旧的 `media-collection` 数据、媒体审批或展示能力。它只规定不同问题使用不同投影，避免再次把文章图、产品舞台和架构模型混成一张图。

## 8. 评价当前实现是否“充分使用 LikeC4”

结论：此前没有充分使用。

我们使用了 LikeC4 的源文件/CLI生成链路，却没有使用它真正有价值的产品能力：

- 多视图与不同层级的架构投影；
- 对象类型、边界和关系语义；
- 节点进入下一视图的导航；
- 官方 React/Web Components 的交互与可访问性基础；
- 以同一模型生成可探索的架构，而不是只导出一张通用 Graphviz 图。

这不是用户把我们限制得太多，而是我们在成本约束下过早选择了错误的最小方案。之后应以“最小的正确能力”为目标，而不是以“最小的静态产物”为目标。

## 9. 验收合同（DRAFT）

### 产品与视觉

- 总览、业务架构、数字化实现和至少一个深层视图各自回答单一问题；
- 视图之间存在可理解的进入、返回和当前层级标识；
- 节点、边界、关系标签、边类型和中文文案可读；
- 1440、1024、768、390、320 均无横向溢出；移动端不把完整桌面图压成不可读缩略图；
- hover/focus/click 不引起布局晃动、节点重排或关系线消失；
- 旧文章链接和新架构视图链接都有稳定降级路径。

### 内容与事实

- 每个 view 有明确的事实源、抽象层级、读者问题和非目标；
- 业务事实、系统结构、操作流程、事件、结果和反馈不混为同一种关系；
- xingbuild 不复制 Robotaxi 权威业务对象，Robotaxi 版本/commit 是上游锚点；
- 文章内容 task 只修改已批准文章和图源，不改页面组件或架构运行时。

### 工程与运行

- LikeC4 模型校验、视图生成和运行时加载必须有自动检查；
- 生成失败不得复用旧图或旧 manifest；
- 公开页面有静态/文本降级；
- 控制台 error/warning 为0，键盘和触控路径成立；
- 不以截图单独作为验收证据，必须同时检查真实 DOM、几何、导航和来源边界。
